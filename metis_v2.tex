\begin{abstract}
Symbol tables are a core compiler data structure whose physical memory footprint and lookup latency directly govern execution efficiency under severe resource constraints. Modern 64-bit systems rely on \texttt{std::unordered\_map} with Short String Optimization (SSO), storing small identifiers ($\le 15$~bytes) without secondary heap allocations. In this paper, we investigate the fundamental memory and latency trade-offs of adaptive symbol-table representations in embedded compiler and runtime environments. We formulate the primary research question: \emph{Under what workload conditions can adaptive symbol-table name representations overcome the structural memory efficiency of an embedded conventional hash-table baseline while satisfying a latency constraint?}

We present \texttt{SymTabV3}, an adaptive scope-aware symbol table that dynamically assigns symbols to \textsc{Inline}, \textsc{Interned}, or front-coded \textsc{Compressed} representations with zero-allocation stack buffer decoding. We derive a closed-form analytical break-even model: for identifiers longer than the SSO threshold ($L > 15$\,B), adaptive storage beats Conventional hash tables when the live duplication ratio satisfies $k > k_{\text{breakeven}} = (2L + 86)/(L + 13)$. We evaluate our model using physical allocator heap tracking (\texttt{malloc\_usable\_size}) across four real embedded workloads (\textsc{FreeRTOS}, \textsc{Arduino}, \textsc{Zephyr}, \textsc{ESP-IDF}), 20 host software corpora, and controlled synthetic experiments (Workloads A--F).

On the large \textsc{Zephyr} workload (2.6M events, 228,739 unique symbols), \texttt{SymTabV3} reduced physically measured final heap by 20.2\% (13.52\,MB) relative to the embedded conventional baseline (53.39\,MB vs 66.91\,MB final heap; 57.89\,MB vs 76.37\,MB peak heap). This reduction was achieved with sub-microsecond median lookup latency ($p_{50} = 0.066\,\mu\text{s}$), while the $p_{95}$ latency increased from $0.125\,\mu\text{s}$ to $0.228\,\mu\text{s}$ ($1.824\times$). Thus, the architecture demonstrates a measurable RAM advantage in the large-scale embedded regime, but does not satisfy the $1.25\times$ $p_{95}$ latency constraint due to measured reconstruction/copy overhead. Additionally, we evaluate \texttt{SymTabV4} as a disclosed negative result, showing that side-table container overheads ($T_{\text{table}}$) erode core scalar field savings across real identifier mixes.
\end{abstract}

\section{Introduction}
Compilers and language interpreters repeatedly create, resolve, and reclaim symbolic bindings during lexical, syntactic, and semantic analysis \cite{aho}. A symbol table maps identifier names to binding metadata across nested lexical scopes. In resource-constrained embedded systems---such as microcontroller toolchains, real-time operating systems (RTOS), and on-device interpreters---available RAM is severely limited.

In desktop and server host compilers (e.g., LLVM \cite{lattner2004llvm}), standard C++ string implementations rely on Short String Optimization (SSO) \cite{meyers2001effective, sutter2004exceptional}. Identifiers up to 15 bytes are stored directly inside the 24-byte string structure, avoiding heap allocations. Consequently, conventional hash maps (\texttt{std::unordered\_map<std::string, SymbolMeta>}) pay zero secondary heap string allocation cost for short names.

In embedded environments, however, secondary heap overheads and container metadata can consume a significant fraction of total memory. While string interning \cite{gosling2014java, vanrossum2009python} and front-coded block compression \cite{witten1999managing, brisaboa2011compressed} reduce string redundancy, their physical RAM savings and tail-latency costs under realistic scope lifecycles have lacked rigorous physical allocator measurement.

In this work, we formulate and address the following central research question:
\begin{quote}
\emph{Under what workload conditions can adaptive symbol-table name representations overcome the structural memory efficiency of an embedded conventional hash-table baseline while satisfying a latency constraint?}
\end{quote}

We make the following main contributions:
\begin{enumerate}
    \item \textbf{Adaptive Architecture (\texttt{SymTabV3})}: We present a C++ symbol table architecture featuring scope-lifetime slot recycling, 3-tier representation routing (\textsc{Inline}, \textsc{Interned}, \textsc{Compressed}), 1-byte hash fingerprints, and zero-allocation stack buffer decoding.
    \item \textbf{Analytical Cost \& Break-Even Model}: We derive closed-form memory equations proving that for $L \le 15$\,B no positive break-even live duplication ratio $k$ exists, whereas for $L > 15$\,B, interning breaks even when $k > (2L + 86)/(L + 13)$.
    \item \textbf{Embedded Memory Advantage}: On the large \textsc{Zephyr} RTOS workload, \texttt{SymTabV3} achieves a 20.2\% (13.52\,MB) physical final heap reduction (and 24.2\% peak heap reduction) over an optimized embedded conventional baseline.
    \item \textbf{Quantified Memory/Latency Trade-off}: We demonstrate sub-microsecond median lookups ($p_{50} = 0.066\,\mu\text{s}$) on \textsc{Zephyr}, while reporting that $p_{95}$ tail latency increases to $0.228\,\mu\text{s}$ (vs $0.125\,\mu\text{s}$ for the embedded conventional baseline), failing the $1.25\times$ $p_{95}$ gate due to measured reconstruction/copy overhead.
    \item \textbf{Disclosed Negative Architectural Result (\texttt{SymTabV4})}: We present \texttt{SymTabV4} (representation-conditional metadata) as a disclosed negative result, showing that sparse side-table allocation floors ($T_{\text{table}}$) outweigh core struct savings across real representation mixes.
    \item \textbf{Controlled Synthetic \& 20-Corpus Host Validation}: We confirm theoretical predictions via synthetic microbenchmarks A--F ($k \ge 3.33$ at $L=32$\,B) and 20 host software corpora.
\end{enumerate}

\section{Background and Motivation}

\subsection{Conventional Symbol Tables and SSO}
A conventional symbol table uses a hash map from string keys to symbol attributes. In 64-bit systems, a \texttt{std::string} instance occupies 32 bytes (or 24 bytes under libc++), consisting of a pointer, length, and capacity/inline buffer. When identifier length $L \le 15$ bytes, characters reside inside the inline buffer (SSO). For $L > 15$ bytes, \texttt{std::string} allocates a heap buffer of size $L + 1$ bytes plus allocator header overhead $H \approx 16$\,B.

In host standard libraries, \texttt{std::unordered\_map} node allocations incur node overhead ($S_{\text{node}} \approx 32$\,B). For short names ($L \le 15$\,B), Conventional pays only metadata and node footprint:
\begin{equation}
M_{\text{conv\_host}}(k, L) \approx k \cdot (S_{\text{meta}} + S_{\text{node}}) \quad \text{for } L \le 15\text{\,B}
\end{equation}

For embedded targets, we construct \texttt{EmbeddedConventional}, a compact baseline combining 16-byte fixed entries, a contiguous byte arena, and an open-addressing slot index.

\subsection{String Interning}
String interning maintains a global pool of unique string instances. Each symbol record stores a 4-byte pool index. However, interning incurs two fixed costs: 1) a global pool vector; 2) a lookup map (\texttt{poolLookup\_}) paying node overhead $S_{\text{pool\_node}} \approx 68$\,B per unique name.

The memory for $k$ live occurrences of a unique name of length $L$ under interning is:
\begin{equation}
C_{\text{pool}}(L) \approx 2L + 86
\end{equation}
\begin{equation}
M_{\text{int}}(k, L) \approx k \cdot C_{\text{idx}} + C_{\text{pool}}(L)
\end{equation}
where $C_{\text{idx}} \approx 28$\,B is the index slot overhead.

\section{Related Work}

\subsection{Compiler Symbol Tables}
Scope management and binding resolution have been studied since early structured language compilers \cite{aho, hanson1980fast, reiss1983practical}. Traditional scope stacks push a hash map on scope entry and pop it on exit. LLVM's \texttt{IdentifierTable} \cite{lattner2004llvm} utilizes a global string map backed by a bump-pointer allocator (\texttt{BumpPtrAllocator}), prioritizing allocation throughput but allowing memory to grow monotonically until compilation completes.

\subsection{String Compression and Dictionary Search}
String interning is standard in runtimes such as Java HotSpot \cite{gosling2014java} and CPython \cite{vanrossum2009python}. For text indexing, front-coded block compression \cite{witten1999managing, brisaboa2011compressed, martinez2016practical} stores lexicographically shared prefixes relative to periodic anchor strings. Succinct data structures \cite{ferragina2000opportunistic, grossi2005compressed} and minimal perfect hash functions (e.g., CHD \cite{botelho2009simple}) achieve optimal static byte density but cannot handle dynamic lexical scope entry and exit.

\subsection{Cache-Conscious Hash Tables}
Open-addressing structures such as Robin Hood hashing \cite{celis1986robin}, Cuckoo hashing \cite{pagh2001cuckoo}, HAT-trie \cite{askitis2007hat}, and burst tries \cite{heinz2002burst} optimize L1/L2 cache locality. \texttt{SymTabV3} complements these by integrating scope-lifetime slot recycling, 3-tier representation routing, 1-byte hash fingerprints, and zero-allocation stack buffer decoding.

\section{Adaptive Symbol-Table Architecture}

\subsection{\texttt{SymTabV3} Core Design}
\texttt{SymTabV3} organizes entries into a scope-managed slot arena. Each slot pays a 32-byte \texttt{PackedEntry} containing scope ID, access counters, representation tags, and a 12-byte payload union:
\begin{itemize}
    \item \textsc{Inline}: Identifiers $\le 12$ bytes are stored inside the slot union (\texttt{inlineBytes[12]}), requiring zero secondary allocations.
    \item \textsc{Interned}: Duplicate or hot symbols store a 4-byte index into a global pool.
    \item \textsc{Compressed}: Long, cold symbols are front-coded in blocks of size $B=32$ with anchor interval $A=8$.
\end{itemize}

Scope exit events (\texttt{exitScope()}) recycle slot indices immediately into a LIFO free-list, preventing fragmentation. To avoid unnecessary decompression during lookup, \texttt{SymTabV3} checks a 1-byte hash fingerprint array (\texttt{fp8}), rejecting non-matching candidates in $O(1)$ time.

\subsection{Zero-Allocation Compressed Path Optimization}
To minimize front-coded decode latency, \texttt{SymTabV3} implements zero-allocation stack buffer decoding (\texttt{decodeToBuffer}). Rather than instantiating temporary \texttt{std::string} objects or executing substring concatenations (\texttt{cur.substr(0, len) + suffix}), prefix and suffix segments are copied directly into a stack-allocated buffer (\texttt{char stackBuf[512]}) via fast \texttt{memcpy}. Furthermore, anchor indices are computed in $O(1)$ time ($\text{start} = \text{slot} - (\text{slot} \pmod A)$), eliminating backward scanning loops. Name equality (\texttt{nameEquals}) performs direct in-place byte comparisons against \texttt{stackBuf}.

\subsection{\texttt{SymTabV4}: Disclosed Negative Result}
To test whether removing hot/cold metadata from \textsc{Inline} entries improves byte density, we designed \texttt{SymTabV4}. \texttt{SymTabV4} reduces \texttt{PackedEntry} from 32\,B to 24\,B (\texttt{CoreEntry}) by moving scalar metadata (\texttt{accessCount}, \texttt{lastAccessEpoch}) to a sparse side table (\texttt{HotMetaTable}). Both node-based and Robin Hood open-addressing side-table variants were implemented and differentially verified against \texttt{SymTabV3} under ASan/UBSan across 200,000 trace steps.

\section{Analytical Cost and Break-Even Model}

Equating $M_{\text{int}}(k, L) < M_{\text{conv}}(k, L)$ yields the theoretical break-even condition:
\begin{equation}
k > k_{\text{breakeven}}(L) = \frac{C_{\text{pool}}(L)}{S_{\text{meta}} + S_{\text{str}}(L) - C_{\text{idx}}}
\end{equation}

For short names ($L \le 15$\,B), Conventional string storage $S_{\text{str}}(L) = 0$ due to SSO. Substituting $S_{\text{str}}(L) = 0$ yields:
\begin{equation}
k > \frac{2L + 86}{24 - 28} = \frac{2L + 86}{-4} < 0
\end{equation}
Because the denominator is negative, \textbf{no positive live duplication ratio $k$ exists for $L \le 15$\,B}. Interning cannot outperform Conventional hash tables on short SSO identifiers.

For long names ($L > 15$\,B), Conventional pays heap allocation $S_{\text{str}}(L) = L + 1 + H \approx L + 17$. The break-even equation becomes:
\begin{equation}
k_{\text{breakeven}}(L) = \frac{2L + 86}{24 + (L + 17) - 28} = \frac{2L + 86}{L + 13}
\end{equation}
As $L \to 15^{+}$, $k_{\text{breakeven}} \to 4.14$. As $L \to \infty$, $k_{\text{breakeven}} \to 2.0$. For $L = 32$\,B, $k_{\text{breakeven}} = 150/45 \approx 3.33$.

For \texttt{SymTabV4} to beat \texttt{SymTabV3}, core-struct savings across \textsc{Inline} entries must exceed the side table's allocation floor ($T_{\text{table}}$) and entry cost ($S_{\text{hotmeta\_marginal}} \approx 34\text{--}57$\,B):
\begin{equation}
k_{\text{inline}} \cdot 8\text{\,B} > k_{\text{hot}} \cdot S_{\text{hotmeta\_marginal}} + T_{\text{table}}(N_{\text{hot}})
\end{equation}
Because real software codebases maintain $10\%$--$70\%$ non-\textsc{Inline} symbols, $k_{\text{hot}}$ is non-zero, causing side-table overheads to exceed core scalar field savings.

\section{Experimental Methodology}

\subsection{Physical Allocator Heap Accounting}
All heap measurements use a physical allocator interceptor (\texttt{include/heap\_counter.hpp}) overriding global \texttt{operator new} and \texttt{operator delete}. The interceptor queries \texttt{malloc\_usable\_size(p)} to record true physical heap allocations, accounting for system page alignment and chunk rounding.

\subsection{Workload Suite}
We evaluate three distinct workload categories:
\begin{enumerate}
    \item \textbf{Real Embedded Workloads}: Four real-world embedded software event traces: \textsc{FreeRTOS} (227k events, 10,386 unique symbols), \textsc{Arduino} (94k events, 11,000 unique symbols), \textsc{Zephyr} (2.6M events, 228,739 unique symbols), and \textsc{ESP-IDF} (2.2M events, 231,075 unique symbols).
    \item \textbf{Host Software Corpora Characterization}: 20 real software codebases evaluated on 64-bit host systems to assess identifier length distributions and SSO fractions.
    \item \textbf{Synthetic Microbenchmarks (Workloads A--F)}: Controlled experiments varying identifier length $L \in \{4\dots 64\}$\,B, duplication ratio $k \in \{1\dots 20\}$, scope depth, and access skew ($N=30$ seeds).
\end{enumerate}

Throughout this paper, we explicitly distinguish \textbf{peak heap} (maximum RAM allocated during execution) from \textbf{final heap} (residual RAM after processing complete event traces).

\subsection{Physical Memory Victory on Zephyr}
On the large \textsc{Zephyr} workload (2.6M events, 228,739 unique symbols), \texttt{SymTabV3} achieves a clear physical allocator memory victory. \texttt{SymTabV3} reduces final heap consumption by **20.2\% (13.52\,MB)** relative to \texttt{EmbeddedConventional} (53.39\,MB vs 66.91\,MB final heap) and by **34.3\% (27.83\,MB)** relative to \texttt{Interned} (53.39\,MB vs 81.22\,MB final heap). Peak heap memory is similarly reduced by 24.2\% (57.89\,MB vs 76.37\,MB).

Representation routing on \textsc{Zephyr} assigns 213,614 symbols (93.4\%) to \textsc{Inline}, 5,372 (2.3\%) to \textsc{Interned}, and 9,753 (4.3\%) to front-coded \textsc{Compressed}.

\subsection{Quantified Latency Trade-off and Reconstruction Overhead}
The zero-allocation compressed-path optimization reduced \textsc{Zephyr} $p_{95}$ latency from $0.547\,\mu\text{s}$ down to $0.228\,\mu\text{s}$ without altering memory footprint. Median lookup latency remains sub-microsecond ($p_{50} = 0.066\,\mu\text{s}$).

However, comparing \texttt{SymTabV3} $p_{95}$ ($0.228\,\mu\text{s}$) against \texttt{EmbeddedConventional} $p_{95}$ ($0.125\,\mu\text{s}$) yields a ratio of **$1.824\times$**, failing the $1.25\times$ $p_{95}$ latency constraint.

This latency gap is driven by measured reconstruction/copy overhead. During execution, 8.81\% of total lookup operations hit \textsc{Compressed} entries. Reconstructing front-coded members requires copying multiple prefix and suffix segments across block members (mean depth $3.31$ steps to anchor, $p_{95} = 7$ steps). Even with zero dynamic memory allocation, copying multiple memory slices introduces measured reconstruction/copy overhead that prevents satisfying the $1.25\times$ gate.

Quantitatively, \texttt{SymTabV3} trades $0.103\,\mu\text{s}$ of added $p_{95}$ latency for 13.52\,MB of physical final heap saved ($131.26\text{ MB}$ saved per $\mu\text{s}$ of added $p_{95}$ latency).

\subsection{Disclosed Negative Result (\texttt{SymTabV4})}
\texttt{SymTabV4} (representation-conditional side-table metadata) failed to beat \texttt{SymTabV3} on 19/20 real software corpora and lost to Conventional on 20/20. Sparse side-table container allocations ($T_{\text{table}}$) plus marginal entry costs ($\sim 34\text{--}57$\,B) exceed the 8\,B core-struct savings across real identifier mixes.

\subsection{Controlled Synthetic Microbenchmarks (Workloads A--F)}
Synthetic experiments D1 and D2 confirm our analytical model. For $L=32$\,B, interning and \texttt{SymTabV3} beat Conventional on peak heap at $k \ge 3$ (1.09\,MB vs 1.16\,MB) and on final heap at $k \ge 4$ (0.70\,MB vs 1.44\,MB), validating the theoretical break-even threshold $k_{\text{breakeven}} = 3.33$.

\subsection{Supporting Host-Side 20-Corpus Characterization}
On 64-bit host systems, \texttt{ConventionalHost} (\texttt{std::unordered\_map}) achieves the lowest physical heap footprint on 20/20 real software corpora. Real host codebases are heavily dominated by short SSO identifiers ($59\%$--$76\%$) and low live duplication ($k < 1.5$), placing them strictly inside Conventional's optimal memory regime.

\section{Discussion and Workload Boundaries}
Our findings establish clear application boundaries for symbol table architectures:
\begin{enumerate}
    \item \textbf{Host Compilers \& Short Workloads}: When short SSO identifiers dominate ($L \le 15$\,B) and live duplication is low ($k < 1.5$), Conventional hash tables are optimal.
    \item \textbf{Large-Scale Embedded Workloads}: When scale and identifier lengths are large ($L > 15$\,B, $N > 200\text{K}$), adaptive front-coding (\texttt{SymTabV3}) achieves significant physical RAM savings (20.2\% / 13.52\,MB on \textsc{Zephyr}).
\end{enumerate}

\section{Limitations}
1) Front-coded block decompression introduces measured reconstruction/copy overhead during tail lookups;
2) Global pool strings persist for compilation unit lifecycles;
3) 64-bit hash fingerprints carry a theoretical collision probability of $\approx 4 \times 10^{-10}$ at 260,000 symbols.

\section{Conclusion}
On the large \textsc{Zephyr} workload, \texttt{SymTabV3} reduced physically measured final heap by 20.2\% (13.52\,MB) relative to the embedded conventional baseline. This reduction was achieved with sub-microsecond median lookup latency, while the $p_{95}$ latency increased from $0.125\,\mu\text{s}$ to $0.228\,\mu\text{s}$. Thus the architecture demonstrates a measurable RAM advantage in the large-scale embedded regime, but does not satisfy the $1.25\times$ $p_{95}$ latency constraint.
