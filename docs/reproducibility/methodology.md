# Methodology

## Toolchain actually used (verified, not assumed)

- Compiler: `g++.exe (MinGW.org GCC-6.3.0-1) 6.3.0` -- an old toolchain. It
  compiles `-std=c++17` without erroring on basic syntax, but **does not ship
  C++17 standard-library headers** (`<optional>`, `<variant>` fail to
  resolve). The whole codebase therefore deliberately targets **C++14**, which
  this toolchain supports fully; no CMake or `make` were available in this
  environment either, so the build is a flat `g++` invocation (`build.sh`).
- No unit-test framework is installed; `tests/smoke_test.cpp` is a small
  hand-rolled `assert`-and-count harness, not a placeholder for "real tests
  later" -- it is the actual correctness check this project runs
  (`ALL TESTS PASSED` / exit 0, or a nonzero-failure count and exit 1).

## "Tracked Memory" -- what it is and is not

Every memory number this project reports (in the demo, the CLI output, and
every CSV) is a **modeled, deterministic sum of per-entry byte costs**,
computed in `MemoryTracker` (`include/memory_tracker.hpp`) from data the
program actually stores: `sizeof(std::string)` control-block size, the real
length of the characters actually held, a fixed per-representation bookkeeping
constant (documented per representation below), and nothing else. It is
**not** an OS-level RSS measurement, not `malloc_usable_size`, and not
allocator-arena overhead. This is stated in code comments everywhere the
number is computed and is why every printed figure is labeled "Tracked
Memory" rather than "memory used".

Per-representation cost model (see `include/*.hpp` for the exact constants):

| Representation | Charged when | Cost |
|---|---|---|
| Conventional entry | insert | `sizeof(std::string) + len+1 + 32` (map key + SymbolMeta + node overhead estimate) |
| Interned (baseline) | first intern of a unique string | `sizeof(std::string) + len+1` once; every symbol referencing it pays `28` (SymbolMeta + 4-byte index) |
| BudgetSym INLINE | insert | `len+1 + 28` |
| BudgetSym INTERNED | first intern of a unique string | `sizeof(std::string)+len+1` once (charged inside `internName()`); every referencing symbol pays `28` |
| BudgetSym COMPRESSED | insert | `1 (shared-prefix-len byte) + suffix.size()+1 + 29` |

A real bug was caught and fixed during development: an earlier version of
`BudgetSym::internName()` never charged the tracker for the shared pool
string's bytes at all (only the baseline `InternedSymbolTable` did), making
every `INTERNED_REP` entry in BudgetSym look artificially cheap. This was
caught by comparing `BudgetSym-Full` against `BudgetSym-NoAdaptiveSelection`
in the ablation study -- before the fix, forcing everything to `INTERNED_REP`
(`NoAdaptiveSelection`) used *less* tracked memory than the adaptive policy,
which made no sense (the adaptive policy should never do strictly worse than
"just always intern" on memory, since it only chooses INTERNED when nothing
better applies). Fixed in `include/budget_sym.hpp`, verified with the smoke
test and by re-running the full benchmark + ablation; results in
`results/` reflect the fixed accounting.

## Timing -- a second real toolchain bug, also caught and fixed

`std::chrono::steady_clock` on this exact toolchain does not work: two
back-to-back `now()` calls report `0ns` apart, and a timed
1,000,000-iteration loop measured `0us`. Using it would have made every
latency column either exactly `0` or noise -- indistinguishable from
fabricating numbers. `include/hires_timer.hpp` uses
`QueryPerformanceCounter` directly on Windows (verified working: 10MHz
counter, the same loop test gives a sane, nonzero, reproducible figure) and
falls back to `std::chrono::steady_clock` on any platform where it hasn't
been observed to be broken. All `*_us` columns in `results/benchmark_results.csv`
and `results/ablation_results.csv` come from this timer, always averaged over
a batch of repeated operations (never a single call), so the number stays
above the ~100ns hardware counter resolution.

## Dataset generation (deterministic, seeded)

All 8 benchmark datasets (`src/benchmark_main.cpp`) are generated with a
fixed-seed `std::mt19937`, so re-running `./src/benchmark.exe` reproduces
identical identifier sets and (modulo timing jitter) memory numbers exactly.
One dataset design choice worth stating explicitly: `decide()`'s prefix-
similarity signal only compares an identifier against the **one inserted
immediately before it** (mirroring a real compiler processing declarations in
source order, not a global search). The `high-prefix-similarity` dataset was
initially generated by round-robin-cycling 5 unrelated prefixes item-by-item,
which meant adjacent identifiers almost never actually shared a prefix --
a mismatch between the dataset's name and what it tested, caught by
inspecting the resulting compression ratio (1.13x, barely above the interned
baseline, for a dataset that should showcase compression) before it made it
into the reported results. Fixed by grouping same-prefix identifiers into
contiguous runs; the corrected dataset produces BudgetSym's best compression
ratio in the whole benchmark (2.37x).

## What "smoke test" vs "benchmark" vs "ablation" each check

- `tests/smoke_test.cpp`: correctness only (shadowing works, scope
  reclamation actually removes entries and lookup reflects it, a compressed
  identifier decodes back to exactly the string that was inserted, promotion
  actually changes representation and preserves lookup correctness). No
  timing, no memory comparison.
- `src/benchmark_main.cpp`: performance/memory comparison of all three
  implementations across 8 workload shapes, written to
  `results/benchmark_results.csv`.
- `src/ablation_main.cpp`: isolates which BudgetSym mechanism (adaptive
  scope reclamation, access-frequency promotion, representation selection
  itself) is responsible for how much of the benefit, on one fixed shared
  workload, written to `results/ablation_results.csv`.
